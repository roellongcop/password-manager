Keyring form fixtures

Serve this file (node tools/serve.js) rather than opening it from disk: content scripts only run on http/https unless file access is enabled for the extension. Each section is a login shape the detector has to cope with.

1. Plain form

The easy case: a real <form> with labelled fields.

2. No form element

Inputs in bare divs, submitted by a click handler.

3. Decoys

A search box and a promo code sit next to the real fields; neither should be picked as the username.

4. Two-step login

Username first, password on the next screen — the classic Google shape.

5. Shadow DOM

Fields inside an open shadow root, as a web component would render them.

6. Rendered late (SPA)

The form does not exist at load; it appears two seconds later.

7. One-time code

A 2FA screen on its own, with autocomplete="one-time-code".

8. Sign-up (two password boxes)

Generating a password should fill both boxes.

9. Nothing to go on

No name, id, autocomplete or label on either field. Scoring finds nothing, so the field above the password has to be taken on position alone — otherwise a captured login has no username.

10. Label says "Email address"

The commonest login label there is. It must not be mistaken for a postal address field and discarded.

11. Username, not email

Plenty of sites ask for a username. Three shapes: named plainly, named cryptically with only a label to go on, and labelled in another language.

13. Account already chosen (no username field)

The shape Gmail uses after you pick an account from the list: nothing is typed and there is no username input, only the address on screen. The capture has to read it from the page or the password is saved with no owner.
